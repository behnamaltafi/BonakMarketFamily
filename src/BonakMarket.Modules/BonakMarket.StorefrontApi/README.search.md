# Storefront catalog — web and mobile integration

All routes are under /api/storefront/v1. Guest access is subject to native catalog permissions. Send a valid Bearer access token for customer-specific pricing and cart capabilities; omit Authorization entirely for guests. An invalid token returns 401. Production requires HTTPS. Do not share-cache customer/store-specific responses.

## Products

- GET /products?search=rice&page=1&pageSize=20 — list/browse/search, paginated. Filters: categoryId, brandId, minPrice, maxPrice, inStock, hasDiscount, showOnHomePage, sort (Initial, NameAsc, NameDesc, PriceAsc, PriceDesc, Newest, BestSellers), includePrice. Reset page to 1 when filters change.
- GET /products/suggestions?search=rice&limit=5 — lightweight search-as-you-type, 250–350 ms debounce. Empty/short/disabled terms return 200 with empty items; no price or total count. Limit capped by administrator settings. Cancel superseded requests and ignore stale responses.
- GET /products/facets?search=rice — matchingProducts, category/brand counts, availability counts and nullable priceRange. Send the same filters as the list except page, pageSize, sort and includePrice. Counts are conjunctive (not disjunctive); clear a selected filter to see alternatives. Category counts use direct mappings. Lists can be truncated; use categories/brands for broader selection.
- GET /products/{id} — product details, images, specifications, variants, purchase rules and allowed actions.
- POST /products/{id}/quote — { quantity, variants: [{ variantAttributeId, valueId }] }. Calculate and validate the selected configuration without writing to the cart. Read isValid, code, pricing, warnings and requiresCartValidation even on HTTP 200. No stock reservation. Cart/checkout remain authoritative.

The list now includes availability (available/out_of_stock; sellable includes untracked stock or permitted backorders), minimumQuantity, maximumQuantity, quantityStep, allowedQuantities, quantityUnit (nullable), requiresConfiguration, canAddToCart, hasDiscount (nullable) and isPreOrder. A maximum below the minimum or zero means there is no supported purchase quantity in this API. Quantity is capped at 1000, as in cart and quote. canAddToCart is a capability for the current authenticated customer and minimum purchase; a true result is not a guarantee that a specific variant/quantity or existing cart is valid. When requiresConfiguration is true, use product details and quote; unsupported product types remain unsupported. Guest canAddToCart follows the enabled guest-cart policy and native permissions; a guest cart token is required for actual cart operations.

Price.finalPrice is an indicative **unit price**, calculated at price.pricingQuantity (minimum supported purchase quantity), not a line total. It may differ from quote or cart pricing. Price may be null for forbidden/unavailable price or includePrice=false. hasDiscount follows the native catalog discount flag; it is null without price-display permission. Actual discount amount is in price/quote. For a nonblank search, omitted inStock follows admin availability settings. Explicit true/false selects sellable/unavailable products; disabled variant combinations are excluded from sellability.

Price filters and range use base currency and active catalog/special prices, before tier/customer discounts, tax and variant adjustments. Price bounds are inclusive; products with call-for-price or customer-entered price are not included in bounds. Sorting alone keeps those products at the end. Price/discount filtering and price sorting require price-display permission. Facets priceRange is null without permission or eligible matching prices. priceFilterCurrencyCode describes the currency for bounds; displayed price has its own currencyCode.

All three search endpoints use the same scoped SQL matching and supported configured fields (name, SKU, short description). Simple Persian terms normalize Arabic ي/ك, ordinary spaces and ZWNJ on input and stored/current-language translated values; configured Contains/StartsWith/ExactMatch mode still applies. Other terms use native search parsing. No fuzzy search or external search index is promised. Explicit name sort remains based on stored product name. Search-as-you-type uses a smaller image and omits purchase/price calculations.

## Categories and brands

- GET /categories?parentId=0 — root categories. Positive parentId returns direct children. Omit parentId for a flat paginated list. Optional search and showOnHomePage.
- GET /categories/{id} — same item shape, 404 for missing/inaccessible category.
- GET /brands?search=...&page=1&pageSize=20 — paginated brand list in admin display order; ties by localized name and ID.
- GET /brands/{id} — same item shape, 404 for missing/inaccessible brand.

Category items include parentId, displayOrder, hasChildren and showOnHomePage. hasChildren is based on visible children, not the search or page. Hidden/unpublished/deleted ancestor branches and detached categories are excluded using the native tree path. Product category filters respect the visible branch and non-system category mappings. Names use current-language translation with stored-name fallback. All catalog image URLs are produced by native media services in page-sized batches; missing, deleted, hidden and transient images return null. Category/brand thumbnails use configured sizes. Resolve relative URLs against the API origin and render a client placeholder for null.

## Migration

Old /search, /search/instant and /search/facets routes remain removed. Use /products, /products/suggestions and /products/facets. This change additionally removes GET /products/{id}/variants (use detail.variants) and GET /products/{id}/price (use detail.price for the indicative unit price or POST /products/{id}/quote for quantity/variant validation and pricing). Update web/mobile clients before deployment. All other catalog contracts remain additive.

HTTP 400 validation, 401 invalid token, 403 permission, 404 missing/inaccessible entity, 503 unavailable store use the existing problem response contract. Do not retry invalid requests automatically. FullDescriptionHtml is HTML content; render through the client's safe HTML policy.

## Home catalog (phase 1)

- `GET /products?sort=BestSellers&page=1&pageSize=10`: descending ordered quantity over the previous 90 days in the current store, using native `SelectAsBestsellersReportLine` and joining to the visible catalog before paging. Products without qualifying sales are excluded; ties use product ID (no price-dependent ordering). Existing filters remain in force. No order counts or customer IDs are returned.
- `GET /me/frequently-purchased?page=1&pageSize=10`: Bearer only, requires Orders and Catalog permissions. Uses the last 365 days of the authenticated customer's orders in the current store, ranks by distinct order count, then total quantity, then product ID. Uses the shared catalog filters (search, categoryId, brandId, minPrice, maxPrice, inStock, hasDiscount, showOnHomePage, includePrice), price ACL and paging. The sort is fixed. Empty history yields an empty page; current stock and price use the same mapper as the catalog.
- Both rankings consider completed orders (except fully refunded/voided payments) and paid processing orders; ignore deleted, pending, cancelled, fully refunded and voided orders and nonpositive lines. Partial refunds are not attributed to lines, so these are gross ordered quantities, not net sales. Windows use UTC creation date. This is an explicit customer-facing eligibility policy, narrower than the native all-time admin/MVC report.
- `GET /products?showOnHomePage=true`: reuses native `HomePageProductsOnly`, `ShowOnHomePage` and `HomePageDisplayOrder`; the default order is the administrator's order with product ID tie breaker. Explicit sorting overrides it. Facets support the same filter. Use bootstrap `features.showBestsellersOnHomepage` and `features.numberOfBestsellersOnHomepage` for the home section; the generic BestSellers list is not disabled by that layout preference.
- `price.retailPrice`, `price.savingPercentage`, `price.savingAmount`, `price.savingReference` and `price.taxInclusive` come from native `IPriceCalculationService`. All unit prices use the same currency and tax basis; `discountPercentage` is the native saving against regular price only, not a rule discount. The existing `hasDiscount` filter represents native assigned-discount semantics, not MSRP savings.
- Configure **Admin → Settings → Storefront API** (or module Configure). Select a package-size specification and the native quantity unit that explicitly denotes a package. Numeric options use `NumberValue`; assign exactly one per product. The package count remains nullable if missing, duplicate, deleted or invalid. The API derives `consumerPrice` per individual item only when the actual sale unit matches the selected package unit, a valid package count is present and the native retail price is available and permitted. `consumerPriceCurrencyCode` equals the calculated native price currency. No separate price specification, currency setting, conversion, or stored price is needed. The native `price.retailPrice` always describes the sellable unit; cart quantity continues to mean sellable units. The per-item reference is not a cart quote. Do not use legacy consumer-price specifications as financial data; remove any created during development or migrate deliberately into native ComparePrice with an IsRetailPrice label after verifying its sale-unit basis.
- No new tables, migrations, Core/OData/ERP changes or appsettings keys. Global configuration is stored in native `WholesaleCardSettings`. Refresh module language resources via the native import mechanism for already-installed modules before using the localized settings page.

- Deploy validation: execute the ranking and metadata queries against SQL Server, including store/customer isolation, price ACL, duplicate specification mappings, page boundaries and paid/refunded/cancelled orders. Test ranking latency against production-sized order histories before rollout.
